# Mailbox protocol v1

Every persisted message is an immutable envelope:

```json
{"version":1,"id":"msg_32_lowercase_hex","thread_id":"thr_32_lowercase_hex","seq":1,"parent_id":null,"direction":"inbound","text":"request","data":{"arbitrary":"json"},"created_at":1760000000.0}
```

IDs are opaque server UUID4-derived identifiers. `seq` is a global mailbox SQLite
`integer primary key autoincrement`; serialized write transactions allocate
committed monotonically increasing order. Timestamps are diagnostic wall-clock
seconds, never ordering keys. IDs/order/time/version/direction are generated by the
server, not obtained from text/data. There is no message edit/delete command.

`post` creates an inbound message and, if `thread_id` is omitted, a new thread in
the **same transaction**. Optional generic metadata belongs to that thread, is
immutable, and is returned separately by read-thread. Existing threads reject
metadata writes. No task lifecycle fields have special meaning. Parent references
must exist in the explicit same thread. Outbound `reply` always requires explicit
thread and parent IDs; no most-recent selectors, names or implicit threading.

An optional mailbox-global idempotency `key` is 1..128 ASCII alphanumeric or
`._:-` characters. A serialized transaction compares the canonical request,
including create-thread intent, before allocating anything. Identical retries
return the original envelope; changed payloads fail without writes. JSON object
key order is ignored; meaningful values (including omitted/default metadata
semantics) are otherwise preserved. Keys and history are retained indefinitely.
Choose stable keys for external retries and replies.

## Limits and errors

- Text: 16,384 UTF-8 bytes; data: 16,384 canonical JSON UTF-8 bytes.
- New-thread metadata: JSON object, 4,096 encoded bytes.
- Input files/stdin: read at most 65,537 bytes, reject above 65,536.
- Pages: default 20, max 100 messages. JSON/full bodies remain bounded by page
  size; escaped JSON text can be larger than plaintext. No unbounded dump command.
- Cursor: exclusive global sequence integer `0..9223372036854775807`.
  `next_cursor` is the last returned sequence only if another matching row exists.
  Use the same thread/pending selector when continuing. There are no snapshots
  across pages; new messages may appear, and ack can change pending membership.
- JSON numbers must be finite; duplicate keys, malformed JSON, unknown request
  fields, invalid references, bool-as-integer selectors and out-of-range pages fail.
- Expected CLI failures exit 2 with lowercase stderr diagnostics; stdout on success
  is either compact human output or explicit JSON. `consume`/`codex` emit JSON lines.

Use `inbox-axi --help` and `inbox-axi COMMAND --help` for exact options. Supported
commands: init, post, reply, read-thread, pending, ack, ack-status, status, consume,
delivery-state, retry, codex, setup, doctor, uninstall.

`pending` is unacknowledged **inbound** input only, not all unfinished work.
Read-thread contains both directions forever. `ack MESSAGE_ID` is idempotent,
records explicit incorporation, never deletes history or marks a task complete.
Replies do not ack. There is no auto-forwarding of assistant output.


`ack-status MESSAGE_ID [MESSAGE_ID ...]` reads incorporation flags for 1..8
explicit inbound message IDs. It never acknowledges input or returns body content.
The Pi adapter uses this bounded read to distinguish trusted explicit incorporation
from mere transport writes or native observations.

## Claude channel routing

The normal native channel targets the active conversation attached to its launch,
including conversation replacement. Notification metadata contains generated
message/thread IDs, server sequence, `routing: active_conversation` and a diagnostic
process `launch_id`, never a claimed current Claude session UUID. Body text/data
cannot overwrite these fields. Each notification includes an explicit thread-read
CLI argv reminder. Restore thread history and any generic associated task context
before processing, replying or acknowledging in a new/current conversation.
Optional thread metadata can carry an operator-owned task reference, but inbox-axi
never interprets it as a task lifecycle or performs automatic mapping. Native
notification writes are not receipts, registration confirmation or incorporation.
